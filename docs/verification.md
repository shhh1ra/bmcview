# Проверка порта

Протокол восстановлен по декомпиляции, а декомпиляция бывает неверной (см. журнал, 2026-10-28:
цикл двухцветного RLE). Поэтому опираемся на три уровня проверки.

## 1. Юнит-тесты (`cargo test`)

Ручные примеры для каждого типа блока, фрейминга, CRC (эталон каталога CRC), сборки кадров
(в порядке, вразнобой, дубликаты, чередование двух кадров), ограничителя запросов I-кадра.

Для JPEG используется блок, собранный вручную: все коэффициенты нулевые, ожидается ровный серый 128.
Это проверяет синтез заголовка и согласованность таблиц Хаффмана без внешнего кодировщика.

## 2. Сверка с оригинальным кодом (oracle)

Оригинальные Java-классы запускаются через Nashorn (`jjs`) из JRE, которая идёт с клиентом.
Компилятор Java для этого не нужен.

| Скрипт | Что делает | Эталон | Тест |
|---|---|---|---|
| `tools/oracle/dump-method.js` | печатает байткод метода встроенным в JRE ASM — для мест, где декомпиляции нельзя доверять | — | — |
| `tools/oracle/gen-video-golden.js` | строит случайные кадры из блоков всех типов (включая заведомо ошибочные), прогоняет их через оригинальный `ImageDecoder.decodeRLEorJPEG1`, пишет CRC32 пикселей каждого блока | `core/tests/golden/video.txt` | `core/tests/golden_video.rs` |
| `tools/oracle/gen-crypto-golden.js` | прогоняет оригинальный `AESHandler`: encodeKey, kvm_key из KVM_KEY_SET (SHA1/SHA256), шифрование ввода и команд, расшифровку видео, режим `compress=0` | `core/tests/golden/crypto.txt` | `core/tests/golden_crypto.rs` |

Тест видео требует совпадения не только пикселей, но и исхода: если оригинал на кадре выбросил
исключение, порт тоже обязан вернуть ошибку. После такого кадра оба декодера пересоздаются: оригинал
оставляет частично обновлённое состояние, порт — нет (см. architecture.md, Р4).

Генераторы детерминированы (фиксированный seed), поэтому повторный запуск даёт тот же файл.

Эффективность сверки проверена мутацией: если инвертировать флаг «не менять цвет» в двухцветном RLE,
тест видео падает на первом же двухцветном блоке.

Важно: каталог оригинального клиента (`D:\kvm_client_windows`) используется **только для чтения**.
Классы берутся из распакованной копии (`../extract/pe`), из JRE запускается только `jjs`.

```bash
JJS=/d/kvm_client_windows/jre/bin/jjs.exe
CLASSES=../extract/pe

# байткод метода
$JJS tools/oracle/dump-method.js -- $CLASSES/com/library/decoder/ImageDecoder.class decodeRle

# пересборка эталонов
$JJS -cp $CLASSES tools/oracle/gen-video-golden.js  -- core/tests/golden/video.txt 12345
$JJS -cp $CLASSES tools/oracle/gen-crypto-golden.js -- core/tests/golden/crypto.txt
```

`../extract/pe` — распакованное содержимое `KVM.exe` (7-Zip извлекает вложенный jar).

## 3. Дампы трафика

Запись сессии штатного клиента с реальным RH1288 V3. Первый дамп снят 2026-10-29.

**Как снять** (Windows, PowerShell от администратора, без установки Wireshark):

```powershell
pktmon filter remove; pktmon filter add bmc -i <IP BMC>
pktmon start --capture --comp nics --pkt-size 0 -f kvm.etl -s 2048
# ... сессия в штатном клиенте ...
pktmon stop; pktmon etl2pcap kvm.etl -o kvm.pcapng
```

`--pkt-size 0` обязателен: по умолчанию `pktmon` обрезает пакеты до 128 байт.

**Как прогнать через ядро.** Выгрузить из дампа сырой поток BMC → клиент (порт 2198) в файл и выполнить:

```bash
cargo run --release -p ibmc-core --example replay -- stream.bin last.ppm
```

Пример печатает статистику по типам сообщений, кадрам и ошибкам и сохраняет последний кадр.
Результат первого дампа: 770 кадров, 0 ошибок декодирования, картинка совпала с экраном сервера.

**Дампы в репозиторий не кладём.** На наших серверах `compress=0`: клавиатура шифруется ключом,
который виден в самом трафике, а видео не шифруется. По дампу можно прочитать набранные пароли
и увидеть экран сервера. Поэтому эталонный интеграционный тест «дамп → кадры → контрольные суммы»
будет на синтетическом потоке или на дампе, снятом специально (чистый экран, без ввода паролей).

Прошивка заморожена, поэтому однажды записанный дамп остаётся эталоном навсегда.
