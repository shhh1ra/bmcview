## 2026-10-28 (вечер) — сверка с оригиналом, криптография

### Сделано
- **Эталоны из оригинального кода.** Генераторы на Nashorn (`tools/oracle/gen-*-golden.js`) прогоняют
  классы оригинального клиента и пишут ожидаемые результаты. Компилятор Java не нужен: `jjs` есть в JRE,
  которая идёт с клиентом.
  - видео: 75 случайных кадров на 5 разрешениях (64×64 … 450×130), все типы блоков; 57 кадров
    декодируются, 18 оригинал отвергает (намеренно битые блоки и ссылки на соседей без палитры);
  - криптография: 43 случая (encodeKey, kvm_key, шифрование ввода и команд, расшифровка, `compress=0`).
- `core::crypto`: PBKDF2 (SHA1/SHA256), AES-128-CBC с нулевым дополнением, wordswap, `UserKeys`
  (decrykey → encodeKey, kvm_key, ключ переподключения), `SessionKey` (ввод, команды, видео),
  `encrypt_legacy` для `compress=0`.
- Результат: **порт совпал с оригиналом во всех случаях с первого прогона**: пиксели более 300 блоков,
  исходы всех 75 кадров, все 43 криптослучая.
- Мутационная проверка: инвертированный флаг в двухцветном RLE роняет сверку. Значит, тест не пустой.
- Clippy без замечаний. Всего 40 тестов.

### Выяснилось
- Пароль для KDF из `KVM_KEY_SET` оригинал собирает как `(char)byte` со **знаковым** расширением,
  а SunJCE кодирует пароль в UTF-8. Байты ≥ 0x80 превращаются в U+FF80..U+FFFF (3 байта UTF-8).
  Повторено в `java_password_from_bytes` и проверено эталонами с произвольными байтами.
- Nashorn — это ES5: нет `Math.imul`, `Long` из Java нужно явно приводить к `Number`.
  Для детерминированных случайных данных используется `java.util.Random`.

### Окружение
- Пока установщики ждали подтверждения UAC, ядро собиралось GNU-тулчейном Rust
  (`stable-x86_64-pc-windows-gnu`): у него свой линкер, права администратора не нужны.
- После подтверждения установлены Node.js 24.22.1 (LTS) и VS 2022 Build Tools 17.14 (C++).
  Ядро собирается и проходит все тесты на основном тулчейне `stable-x86_64-pc-windows-msvc`.

## 2026-10-28 — старт: каркас, фрейминг, видео

### Сделано
- Создан проект `ibmc-console`: cargo workspace, крейт `core` (`ibmc-core`), документация.
- `core::crc` — CRC-16/XMODEM, проверен эталоном `"123456789" → 0x31C3`.
- `core::framing`:
  - исходящие пакеты (`FE F6 | len | codeKey | CRC | payload`);
  - вариант с 24-байтным encodeKey для CONNECT_BLADE;
  - потоковый разборщик входящих `FE F6 00 LL`, порт `KVMUtil.diviStreamNew` вместе с правилом
    ресинхронизации по недопустимой длине.
- `core::video`:
  - `fragment_from_message` — извлечение фрагмента из сообщения 0x02 (с расшифровкой при `compress=1`);
  - `Assembler` — порт двухбуферной сборки кадров (`isComplete/setVar/setPremBuffer/setMinorBuffer/combine`)
    и фильтра «кадр не изменился»;
  - `IFrameThrottle` — порт ограничения запросов I-кадра (500 мс);
  - `Decoder` — порт `decodeRLEorJPEG1`/`decodeRle`: RLE (сплошной, двухцветный, палитра 3/4,
    наследование палитры слева/сверху), JPEG-блоки, копирование и неизменённые блоки;
  - `jpeg` — синтез заголовка JPEG и декодирование блока.
- Таблицы JPEG (`core/src/video/tables.rs`) генерируются из Java-исходников скриптом
  `tools/gen-jpeg-tables.sh`, а не копируются руками.
- Установка тулчейна на рабочую машину: rustup, VS 2022 Build Tools (C++), Node LTS (через winget).

### Выяснилось
- **CFR неверно декомпилировал цикл двухцветного RLE** в `ImageDecoder.decodeRle`: в его версии цикл
  не продвигается (`m = --m_temp` выполняется всегда). По байткоду (`docs/decodeRle.bytecode.txt`)
  `m_temp--` выполняется только в ветке «в буфере остались биты». Это механизм дочитывания хвоста
  битового потока без чтения новых байт. Порт сделан по байткоду.
  Вывод для процесса: спорные места декомпиляции проверяем по байткоду или прогоном оригинала.
- В заголовке JPEG есть сегмент DRI (интервал рестарта 100). Блок 64×64 в 4:4:4 содержит 64 MCU,
  поэтому маркеров RST в данных блока не бывает.
- Крайние блоки (`zipType` 1 и 3) оригинал хранит целиком 64×64 и обрезает при отрисовке. Отдельная
  логика обрезки в ядре не нужна.
- Нулевой фрагмент с битом7 в байте `[7]` — «кадр не изменился»: дальше `DrawThread` его не передаёт.
  Поэтому ветки diff-кадров в сборщике на iBMC фактически не используются, но портированы для точности.
- Палитра при копировании блока не наследуется (`new ImageBlock()` не копирует `pixColors`).
  Последующий блок «палитра слева, цвета переставлены» от такого соседа в оригинале падает с NPE,
  у нас это ошибка кадра.
