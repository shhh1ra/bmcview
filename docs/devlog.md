## 2026-10-29 (вечер) — клиент: логин, сессия, сеть, UI

### Сделано
- Дамп с сервера по просьбе пользователя убран с диска (в корзину Windows).
- `core::login` — тело запроса и разбор ответа логина. Разбор позиционный, как в оригинале
  (`FindParaFromMsg`), поэтому имена JSON-ключей не нужны. Коды ошибок 131/136/137/144.
- `core::input` — `KeyboardEvent.code` → HID usage, состояние клавиатуры со слотами как
  в оригинале, абсолютные координаты мыши 0..3000.
- `core::session` — сессия как конечный автомат без ввода-вывода: heartbeat 5 с, согласование
  KDF, CONNECT_BLADE через 1 с, ответ на `0x28`, ключ переподключения из `0x40`, ввод для
  `compress=0` и `compress=1`, питание, запросы I-кадра. Последовательность в тесте совпадает
  с записанной сессией байт в байт.
- `app`: логин по HTTPS (rustls + ring, привязка сертификата, решение Р7), сетевой цикл сессии
  с переподключением, бинарный канал видео в UI.
- `ui`: экран входа (недавние хосты без паролей, монопольный режим, предупреждение о смене
  сертификата) и консоль: canvas, клавиатура, мышь, индикаторы, качество, Ctrl+Alt+Del,
  питание с подтверждением, полный экран, значок «без шифрования».
- Тесты: 56 в ядре, 3 в приложении. Сквозной тест сетевого цикла на поддельном BMC проверяет
  подключение, доставку кадра в UI и закрытие сессии.

### Выяснилось
- Коды питания по меню оригинала: `0x20` — принудительное выключение, `0x22` — холодный сброс,
  `0x23` — корректная перезагрузка, `0x25` — корректное выключение. Прежняя догадка про `0x25` была неверной.
- Значения качества на проводе — 40, 50, 70, 80, 90, 100: ползунок 40..90, от 60 и выше шлётся +10.
- `codeKey` — младшие 32 бита `verifyValue`: константа `i` в `KVMApplet` из-за `intValue()` равна нулю.
- Тест нашёл ошибку в собственном UI-сценарии: кнопка «Обновить» через ограничитель I-кадров
  с первого нажатия ничего не отправляла. Теперь отдельная команда без ограничения.

### Не проверено
- Подключение к живому BMC: TLS-рукопожатие (наборы шифров старой прошивки), формат ответа логина,
  вёрстка UI в окне приложения. Встроенная браузерная панель не открыла локальный dev-сервер.
- Режим `compress=1` реализован по декомпиляции, на железе не проверялся (наши серверы — `compress=0`).

### Дальше
- Первый запуск на живом сервере, затем исправления по итогам.
- Перехват системных сочетаний (Win, Alt+Tab, Cmd+Tab) — платформенный захват клавиатуры.
- Пароли в Keychain / Credential Manager.

## 2026-10-29 — первый дамп реальной сессии

### Сделано
- Пользователь снял дамп рабочей сессии штатного клиента встроенным в Windows `pktmon`:
  фильтр по IP BMC, полные пакеты (`--pkt-size 0`), конвертация в pcapng. Wireshark не понадобился.
  Дамп лежит вне репозитория (`kvm-reverse/captures/`).
- Разбор pcapng и сборку TCP-потоков сделал небольшой скрипт на Node. Оба направления
  разложились на пакеты нашим фреймингом без единого лишнего байта.
- `core/examples/replay.rs` прогоняет записанный поток BMC → клиент через `Deframer`, `Assembler`
  и `Decoder` и сохраняет последний кадр в PPM.
  **Результат на реальном видео: 770 кадров 1024×768, 0 ошибок, 0 рассинхронизаций,
  картинка совпала с экраном сервера** (консоль Ubuntu).
- `protocol.md` §7 переписан по реальной последовательности сессии, закрыты три вопроса из §8.

### Выяснилось
- Наши серверы работают в режиме **`compress=0`**. Клавиатура шифруется ключом из `codeKey`,
  а он идёт открытым текстом в каждом пакете. Все 119 пакетов клавиатуры расшифровались.
  Мышь и видео не шифруются вовсе. Вывод: дампы — чувствительные данные (по ним можно прочитать
  набранные пароли), в репозиторий они не попадают. Содержимое нажатий при разборе не выводилось.
- Соединение одно, на порт 2198. `REQ_BLADE_PRESENT`/`BLADE_STATE` и второго TCP нет.
- `0x40` пришёл со 128 байтами, то есть это `reconnKey`. Сессионного `kvm_key` при `compress=0` нет.
- Сервер предлагает три KDF-набора, клиент выбирает PBKDF2-SHA256 × 10000.
- Первые два байта входящих сообщений всегда `00 00`. Heartbeat — ровно 5,00 с.

### Дальше
- Второй дамп: безобидный набранный текст (проверка раскладки HID), смена качества,
  переподключение с `reconnKey`.
- Команды клиента и сессия как конечный автомат — теперь по реальной последовательности из §7.

## 2026-10-28 (ночь, позже) — первый пре-релиз, ветка dev

### Сделано
- Выпущен **v0.1.0-alpha.1** — первый прогон релизного пайплайна:
  Windows `.msi` (2,8 МБ) и `.exe` (1,8 МБ), macOS universal `.dmg` (5,4 МБ) и `.app.tar.gz`.
- Введена ветка `dev`. Схема: работа и локальная проверка в `dev` → PR в `main` → тег на `main`.
- CI переведён с «пуш в `main` и PR» на «PR и по кнопке».
- Actions подняты до версий на Node 24: `checkout@v7`, `setup-node@v7`, `github-script@v9`.
  GitHub предупреждал, что Node 20 снят с поддержки. Ломающие изменения этих версий нас не задевают
  (`require('@actions/github')` в скриптах не используется, кэш npm указан явно).
- Для работы с GitHub установлен `gh` CLI.

### Выяснилось
- Первая сборка под macOS упала без единой строки нашего кода: GitHub не выдал раннер
  («job was not acquired by Runner… even after multiple attempts», нехватка macOS arm64).
  Релиз остался черновиком — страховка «черновик → сборки → публикация» сработала.
  После `gh run rerun --failed` сборка прошла за 6 минут, публикация — автоматически.
- Реальные времена прогонов — в таблице стоимости в `docs/releasing.md`.
  CI на Windows (~10 мин) втрое дольше, чем на macOS (~3 мин).

### Решения
- CI на пуш не запускается: macOS-раннер (×10) тратится один раз на PR, а не на каждый пуш в `dev`.
- PR мерджатся обычным merge commit, чтобы `dev` не расходился с `main` по истории.
- Свой раннер для Windows рассмотрен и отклонён (выбор пользователя): все сборки — на GitHub.

## 2026-10-28 (вечер) — сверка с оригиналом, криптография

### Сделано
- **Эталоны из оригинального кода.** Генераторы на Nashorn (`tools/oracle/gen-*-golden.js`) прогоняют
  классы оригинального клиента и пишут ожидаемые результаты. Компилятор Java не нужен: `jjs` есть в JRE,
  которая идёт с клиентом.
  - видео: 75 случайных кадров на 5 разрешениях (64×64 … 450×130), все типы блоков; 57 кадров
    декодируются, 18 оригинал отвергает (намеренно битые блоки и ссылки на соседей без палитры);
  - криптография: 43 случая (encodeKey, kvm_key, шифрование ввода и команд, расшифровка, `compress=0`).
- `core::crypto`: PBKDF2 (SHA1/SHA256), AES-128-CBC с нулевым дополнением, wordswap, `UserKeys`
  (decrykey → encodeKey, kvm_key, ключ переподключения), `SessionKey` (ввод, команды, видео),
  `encrypt_legacy` для `compress=0`.
- Результат: **порт совпал с оригиналом во всех случаях с первого прогона**: пиксели более 300 блоков,
  исходы всех 75 кадров, все 43 криптослучая.
- Мутационная проверка: инвертированный флаг в двухцветном RLE роняет сверку. Значит, тест не пустой.
- Clippy без замечаний. Всего 40 тестов.

### Выяснилось
- Пароль для KDF из `KVM_KEY_SET` оригинал собирает как `(char)byte` со **знаковым** расширением,
  а SunJCE кодирует пароль в UTF-8. Байты ≥ 0x80 превращаются в U+FF80..U+FFFF (3 байта UTF-8).
  Повторено в `java_password_from_bytes` и проверено эталонами с произвольными байтами.
- Nashorn — это ES5: нет `Math.imul`, `Long` из Java нужно явно приводить к `Number`.
  Для детерминированных случайных данных используется `java.util.Random`.

### Окружение
- Пока установщики ждали подтверждения UAC, ядро собиралось GNU-тулчейном Rust
  (`stable-x86_64-pc-windows-gnu`): у него свой линкер, права администратора не нужны.
- После подтверждения установлены Node.js 24.22.1 (LTS) и VS 2022 Build Tools 17.14 (C++).
  Ядро собирается и проходит все тесты на основном тулчейне `stable-x86_64-pc-windows-msvc`.

### Дальше

- Разбор входящих сообщений: LED, состояние соединения, режим мыши, качество, KVM_KEY_SET, список KDF.

## 2026-10-28 — старт: каркас, фрейминг, видео

### Сделано
- Создан проект `ibmc-console`: cargo workspace, крейт `core` (`ibmc-core`), документация.
- `core::crc` — CRC-16/XMODEM, проверен эталоном `"123456789" → 0x31C3`.
- `core::framing`:
  - исходящие пакеты (`FE F6 | len | codeKey | CRC | payload`);
  - вариант с 24-байтным encodeKey для CONNECT_BLADE;
  - потоковый разборщик входящих `FE F6 00 LL`, порт `KVMUtil.diviStreamNew` вместе с правилом
    ресинхронизации по недопустимой длине.
- `core::video`:
  - `fragment_from_message` — извлечение фрагмента из сообщения 0x02 (с расшифровкой при `compress=1`);
  - `Assembler` — порт двухбуферной сборки кадров (`isComplete/setVar/setPremBuffer/setMinorBuffer/combine`)
    и фильтра «кадр не изменился»;
  - `IFrameThrottle` — порт ограничения запросов I-кадра (500 мс);
  - `Decoder` — порт `decodeRLEorJPEG1`/`decodeRle`: RLE (сплошной, двухцветный, палитра 3/4,
    наследование палитры слева/сверху), JPEG-блоки, копирование и неизменённые блоки;
  - `jpeg` — синтез заголовка JPEG и декодирование блока.
- Таблицы JPEG (`core/src/video/tables.rs`) генерируются из Java-исходников скриптом
  `tools/gen-jpeg-tables.sh`, а не копируются руками.
- Установка тулчейна на рабочую машину: rustup, VS 2022 Build Tools (C++), Node LTS (через winget).

### Выяснилось
- **CFR неверно декомпилировал цикл двухцветного RLE** в `ImageDecoder.decodeRle`: в его версии цикл
  не продвигается (`m = --m_temp` выполняется всегда). По байткоду (`docs/decodeRle.bytecode.txt`)
  `m_temp--` выполняется только в ветке «в буфере остались биты». Это механизм дочитывания хвоста
  битового потока без чтения новых байт. Порт сделан по байткоду.
  Вывод для процесса: спорные места декомпиляции проверяем по байткоду или прогоном оригинала.
- В заголовке JPEG есть сегмент DRI (интервал рестарта 100). Блок 64×64 в 4:4:4 содержит 64 MCU,
  поэтому маркеров RST в данных блока не бывает.
- Крайние блоки (`zipType` 1 и 3) оригинал хранит целиком 64×64 и обрезает при отрисовке. Отдельная
  логика обрезки в ядре не нужна.
- Нулевой фрагмент с битом7 в байте `[7]` — «кадр не изменился»: дальше `DrawThread` его не передаёт.
  Поэтому ветки diff-кадров в сборщике на iBMC фактически не используются, но портированы для точности.
- Палитра при копировании блока не наследуется (`new ImageBlock()` не копирует `pixColors`).
  Последующий блок «палитра слева, цвета переставлены» от такого соседа в оригинале падает с NPE,
  у нас это ошибка кадра.
